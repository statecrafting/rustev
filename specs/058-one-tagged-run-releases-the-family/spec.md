# 058: One tagged run releases the family (amends 021, 031, 053 and 056)

Approved: ratified by the owner on 2026-10-28 (decision A-61). The
approved texts of 021, 031, 053 and 056 are not edited; this spec records
what it replaces in them.

## 1. Purpose

### 1.1 The motivating case: 0.2.0

For 0.2.0, the procedure of 021, 031, 053 and 056 is, in order: the
version-bump pull request (#351); a rehearsal run on `release/next`; a
manifest built by hand from the rehearsal and signed by the owner; a
signed tag naming that manifest's digest; a second full tag run whose
`bind` job must reproduce the rehearsal's bytes; a locally signed
publication instruction for `rustev-release publish`, with a
continuation instruction for any interruption; a separate `npm` job
behind the `npm-publish` Environment; a `hosted-release` step; and the
separately dispatched `qualify.yml`. Working through it took many hours
of owner time, for bytes the workflow already builds and checks in one
run.

The owner then chose (2026-10-28) to skip the candidate for 0.2.0. The
twelve crates were published by local `cargo publish` from the tree of
`main` at `3db28d91` (tree `e7f01a5b`, the commit of the signed tag
`v0.2.0`) between 07:04 and 07:07 UTC on 2026-10-28. The nine npm packages
are being published from the tarballs of rehearsal run 40644111351,
without npm provenance, by owner decision. Those packages therefore lack
the provenance 031 3.9.6 requires, and 0.2.0 is not the evidence this
spec's Acceptance needs.

### 1.2 The model: spec-spine's release

spec-spine releases from one `release.yml`, run on push of a `v*` tag. A
`build` matrix builds each archive once, writes a CycloneDX SBOM (an
empty one fails), requires the OIDC token and attests SLSA build
provenance with the Sigstore bundle attached (its specs 019 and 201).
`publish` creates the GitHub release; `verify-release` downloads it and
verifies every checksum and attestation against the bundle and the
attestation store, failing the run and unpublishing nothing.
`publish-crates` and `publish-npm` run from the same tag, skip any version
already live (a rerun is idempotent) and repackage the build's archives
with no second build. Authority is the tag push alone: the tag's
signature is not checked, crates.io and npm use repository secrets, and
only PyPI uses trusted publishing, in an Environment with no reviewer. A
human merges one version bump, pushes the tag and acts only on a red
run; byte identity is proved by a separate CI workflow.

Rustev keeps more where it is cheap: the owner's tag signature, the
in-run reproducibility check, trusted publishing for both registries, npm
provenance and the fresh-consumer qualification.

## 2. Territory

`.github/workflows/release.yml` and `.github/workflows/qualify.yml`
(non-managed workflows owned in text by 031 3.12 and 056 3.3) and the
release tooling under `tools/rustev-release/`. Changing either workflow
needs the owner's approval of the `statecraft-review-exception`
Environment once (031 3.12); ratifying this spec is not that approval.
Out of scope: the release set's membership, the version policy (021 3.2),
the archive policy, `cargo deny` policy, the container image (still
absent), and any change of decision behavior.

## 3. Behavior

### 3.1 The trigger and the authority

1. `release.yml` runs on `push` of a tag matching `v*`. Its first job,
   `tag`, refuses before any build unless all hold:
   1. the ref is `vX.Y.Z` (a release) or `vX.Y.Z-rc.N` (a candidate,
      3.7), in 053 3.2.2's form;
   2. the tag is annotated and `git verify-tag` passes against
      `tools/rustev-release/allowed_signers` for the owner identity of
      021 3.8;
   3. `X.Y.Z` is `release-set.json`'s `version` at the tagged commit;
   4. the tagged commit is reachable from `main`; and
   5. `ci-gate` concluded `success` on the tagged commit (its merge-queue
      entry, whose commit `main` fast-forwards to).
2. That verified tag is the owner's publication instruction of 021 I-4
   and 031 3.11 for every release after 0.1.0: it names the version and
   the exact commit, and the commit's `release-set.json` names the
   registries and the package set. It replaces the signed instruction of
   056 3.4. Its message names the version and package set; it no longer
   names a manifest digest (021 3.8), because the manifest is made by the
   run (3.2).
3. Publication jobs need one gate job, `approve`, bound to the `release`
   Environment, which has no required reviewer (owner decision, A-61):
   the signed tag alone authorizes the run. The
   publication jobs name their own Environments (`crates-publish`,
   `npm-publish`) only to scope their trusted publishers; those carry no
   reviewer, so no other job waits for a person.
4. A repository tag ruleset lets only the owner create, move or delete
   `v*` tags. A `vX.Y.Z` tag is never moved. It may be deleted and signed
   again on a later commit of `main` only while the run published nothing
   to any registry and created no GitHub release; once anything is
   public, a fix is a new version (021 3.9).
5. `workflow_dispatch` remains as a dry run: every build and check of
   3.2 at the dispatched commit, attesting and publishing nothing. It is
   never a precondition of a release.

### 3.2 One run

1. After `tag`, the run builds every artifact of the release set once at
   the tagged commit: the `.crate` archives (`cargo package --locked` in
   two independent clean checkouts with the commit time as source date,
   the archive policy, and the unpacked tests of 021 3.7 on the pinned
   toolchain and the MSRV), the bindings' addons, the CLI binaries and
   their archives, and the nine npm tarballs.
2. The existing `rebuild` job builds each binary, addon, archive and
   tarball a second time on independent runners; `reproducibility`
   compares every pair byte for byte, `.crate` archives included. Any
   difference fails the run before publication and is explained, never
   normalized away (021 3.7, 031 3.9.3).
3. `sbom` writes a CycloneDX SBOM per `.crate`, tarball and archive and
   refuses an empty one (031 3.9.1); `audit` runs `cargo deny` and the npm
   closure check (031 3.9.2); the changelog is generated as 031 3.10
   says.
4. `manifest` writes `rustev.release-manifest/2` from the artifacts this
   run built and verified (version, commit, tree, tag object id, package
   set and layers, each artifact's name, length and SHA-256, toolchain,
   audit and SBOM digests, limitations) and `SHA256SUMS` over the same
   files. No manifest, signature or artifact is an input to the run.
5. Every artifact, the manifest and `SHA256SUMS` receive a keyless SLSA
   build provenance attestation bound to `release.yml`, the commit and the
   tag (031 3.9.5, Build Level 2), with the Sigstore bundle attached as
   `<file>.intoto.jsonl`. A job that cannot obtain the OIDC token, or whose
   attestation yields no bundle, fails before any publication. These
   attestations replace the owner's detached signatures over the manifest
   and `SHA256SUMS` (021 3.8, 031 3.9.5); the owner's signature is on the
   tag.

### 3.3 Publication

Publication starts only after every job of 3.2 and `approve` pass.

1. **Crates.** `publish-crates` publishes in `release-set.json`'s
   `upload_order` through crates.io trusted publishing (an OIDC token
   exchanged by `rust-lang/crates-io-auth-action`, bound to `release.yml`
   and the `crates-publish` Environment for each of the twelve crates). Before
   each crate it reads the public index: a version already present is
   checked (3.5); an absent one is published with `cargo publish --locked`
   and then must appear in the index with a checksum equal to the run's
   verified `.crate` SHA-256 before the next crate starts. A mismatch fails
   the run. Trusted publishing is required (owner decision, A-61): the run reads
   no crates.io token, and a crate without a trusted publisher fails the
   run before any upload.
2. **npm.** `publish-npm` runs after every crate is observed public (031
   3.1, layer 6), in the release set's npm order (platform packages
   first, then `@rustev/rustev` and `@rustev/rustev-wasm`), with
   `npm publish --provenance` through npm trusted publishing (OIDC, the
   `npm-publish` Environment its publishers are bound to). It publishes
   the run's verified tarballs, never a repack.
3. **GitHub release.** `github-release` creates the release `vX.Y.Z`
   holding the CLI archives, the npm tarballs, the `.crate` archives,
   every SBOM and bundle, the manifest, `SHA256SUMS`, the changelog and
   `publication.json` (3.5). It is the only job with `contents: write`.
4. No job holds `packages: write` (053 3.4.2) or a registry token other
   than the OIDC tokens of trusted publishing.

### 3.4 Verification and qualification

1. `verify-release` downloads the GitHub release's assets and fails the
   run unless every asset of the manifest is present and non-empty, its
   SHA-256 equals the manifest and `SHA256SUMS`, and its attestation
   verifies against its bundle and against the attestation store. For each
   crate and npm package it compares the registry's checksum or integrity
   with the manifest and runs `npm audit signatures` over the npm set.
2. `qualify` is the run's last stage: `release.yml` calls `qualify.yml`
   (which gains `workflow_call`) with the tag. It waits, bounded, for
   index and registry visibility, then runs `qualify.sh` on each platform
   of the CLI and npm matrix exactly as 056 3.3 specifies, with the
   required kinds derived from the run's manifest instead of a signed
   one, and records the lifecycle through `rustev-release qualify`, which
   no longer takes an instruction or a journal.
3. A failure of either stage fails the run and unpublishes nothing; the
   lifecycle stays `released` (021 3.1) and the remedy is the owner's.
   `qualify.yml` stays dispatchable by hand to requalify a published tag;
   a qualification is evidence for that registry state and matrix only
   (021 3.10).

### 3.5 Failure and resume

1. The run is resumed by rerunning its failed jobs under the same tag,
   which reuses the run's verified artifacts. No fresh instruction and no
   journal continuation is needed: the tag still names the same commit
   and set (this replaces 031 3.11.4 and 056 3.4's continuation).
2. Every publication step is idempotent against public state. A crate or
   npm version already present is skipped when its registry checksum
   (crates.io index `cksum`, npm `dist.integrity`) equals the run's
   artifact, and fails the run otherwise. A GitHub release already present
   is accepted when its assets equal the run's, and the run fails without
   replacing anything otherwise (053 3.3.4's rule, now for every release).
3. A full rerun rebuilds; reproducibility (3.2.2) makes its bytes equal,
   and 3.5.2 refuses them if they are not. Nothing is yanked, unpublished,
   retagged or republished by the workflow; a yank needs its own owner
   instruction (021 3.9).
4. The outside-Git publication journal of 021 3.9 is replaced by
   `publication.json` (`rustev.publication-record/1`), written by the
   publication jobs and attached to the release: per artifact, its
   SHA-256, the registry's observed checksum, whether it was published or
   found present, and the time. Tokens never appear in it or in logs.
   `partially published` (021 3.1) is the state of a run whose crates
   job succeeded for some layers and failed for a later one.

### 3.6 What stays

Proposals, never grants (spec 001; 031 3.13; I-3); the release set, its
layers and lockstep version (021 3.2, 031 3.1); 021 3.3 to 3.7 and 031
3.9.1 to 3.9.3 and 3.9.6 for every artifact; the harness and
`rustev.qualification-step/1` of 056 3.3; and the lifecycle of 021 3.1
and I-1, observed as `candidate-verified` when 3.2 passes,
`publication-authorized` when `tag` and `approve` pass, then
`partially published`, `published`, `released` and `qualified` from 3.3
and 3.4. 0.1.0's authority (031 3.11.1) is spent and unchanged.

### 3.7 Candidates become optional

Spec 053 is kept as an option, not a precondition. A signed `vX.Y.Z-rc.N`
tag pushed on a commit of `main` runs the same workflow through 3.2 and
`github-release` as a pre-release, never latest, and stops: no `approve`,
no registry publication, no qualification. Its manifest is the run's own,
so 053 3.1 (the `release/next` rehearsal and the hand-built manifest),
3.2.1's `release-manifest-sha256:` line and 3.3.1's manifest input and
`bind` job are removed. Kept: 053 3.2.2 to 3.2.5, 3.3.3, 3.3.4, 3.4 and
3.5. Retiring candidates was rejected: traveler pins a candidate tag
through a Cargo git dependency (053 3.5), and with one workflow a
candidate costs the owner only a signed tag.

### 3.8 What a human does

1. Merge the version-bump pull request that moves the release set to
   `X.Y.Z` (021 3.2; the PlanId and golden regeneration of 056's version
   move).
2. Sign and push the tag on that commit of `main`:
   `git tag -s vX.Y.Z -m "rustev X.Y.Z"` then `git push origin vX.Y.Z`.
3. Act on a red run: rerun failed jobs, or decide a new version.

Once only, before the first release under this spec: attach crates.io
trusted publishers for the twelve crates and confirm the npm trusted
publishers for the nine packages (workflow `release.yml`, Environments
`crates-publish` and `npm-publish`), create the `release` and
`crates-publish` Environments and the tag ruleset, and remove the `release/next` protection of 053 decision 2.

### 3.9 What is removed

- The rehearsal on `release/next` as a precondition (053 3.1) and its
  branch protection.
- The owner-signed manifest and `SHA256SUMS` as inputs, the
  `release-manifest-sha256:` tag line, `tag-manifest` and `bind` (021
  3.8, 031 3.11.2, 053 3.3.1).
- The second, separate tag run that reproduced another run's bytes.
- The signed publication instruction and its verification in `publish`
  and `hosted-release` (056 3.4, 056 I-1), the instruction and journal
  arguments of `qualify`, the continuation instruction, and local
  `rustev-release publish` as the crates path.
- The `publish-npm` dispatch input and the separate `hosted-release` step.
- 053 as a precondition of any release (3.7).

## 4. Observable negative cases

| Case | Expected |
|---|---|
| A lightweight, unsigned or wrongly signed `v0.3.0` tag is pushed | `tag` fails, naming 3.1.1; nothing builds or publishes. |
| `v0.3.0` while `release-set.json` says `0.2.0` | `tag` refuses: the version differs. |
| The tagged commit is not reachable from `main`, or has no successful `ci-gate` | `tag` refuses before any build. |
| A `.crate`, binary, addon, archive or tarball differs between the two builds | `reproducibility` fails; nothing publishes. |
| An SBOM has no components, or attestation yields no bundle | The run fails before `approve`. |
| The owner rejects the `release` Environment | No publication job runs. |
| A crate or npm version is already public with a different checksum | The job fails; nothing is republished. |
| crates.io lists a just-published crate with a checksum other than the run's | The job fails before the next crate. |
| A GitHub release exists with a differing asset | The job fails and replaces nothing. |
| A published asset's attestation does not verify | `verify-release` fails; nothing is unpublished. |
| A qualification platform reports `not_run` or failing | The run fails; the lifecycle stays `released`. |
| A `vX.Y.Z-rc.N` run | Ends at the pre-release; no registry is touched. |
| A `workflow_dispatch` run | Builds and checks only; attests and publishes nothing. |

## Acceptance

- `tools/rustev-release/` tests break each rule of 3.1.1 once, cover the
  manifest generated from a run's artifacts (3.2.4), and cover 3.5.2 for
  crates, npm and the GitHub release: absent (published), present and
  equal (skipped), present and different (fails).
- A workflow test asserts the `push: tags` trigger, that `approve`,
  `publish-crates`, `publish-npm` and `github-release` follow every job
  of 3.2, that `qualify` is the last job, and that no job holds
  `packages: write` and only `github-release` holds `contents: write`.
- The first release after 0.2.0 is published by one tagged run, every
  npm package with verified provenance, and that run's `qualify` stage
  records the lifecycle as `qualified`. Its run id, tag and release URL
  are recorded here.
- `make gate` passes.
