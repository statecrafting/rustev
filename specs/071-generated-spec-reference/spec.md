# 071: Generated spec reference pages

Approved: ratified by the owner on 2026-11-10 (A-92). Implementation in
progress (increment 1 of 2).

## 1. Purpose

The specs are this repository's contract, but reading one means reading its
Markdown source and running `spec-spine registry` queries to learn its status,
what amends it and what it owns. The README used to restate that status by
hand and drifted for months (#585). spec-spine 0.32.0 can generate one
deterministic reference page per spec (spec-spine specs 166 and 197) and check
the committed pages against a fresh generation. This spec adopts that, so the
per-spec record is browsable on GitHub and cannot drift from its sources.

## 2. Territory

- Establishes `docs/reference/`: the request `request.json`, the generated
  pages `<spec-id>.md`, and the authored index `README.md`.
- Extends spec `001`'s `Makefile` (the `refresh`, `gate` and
  `reference-check` targets and `VERIFIED_SPECS`) and `scripts/acceptance/`
  (071's acceptance group), both additively.
- Increment 2 adds a pull-request-time step to a workflow spec `001` owns
  (3.4); that change is a workflow pull request of its own.

`README.md` links the pages; it is referenced, not owned.

### 2.1 Binding principles

The pages restate declared records. Each carries spec-spine's fixed
limitation statement: a page does not state that code is correct, that a
test ran or passed, or that anything was released. Nothing here changes what
any other spec requires.

## 3. Behavior

### 3.1 The export request

`docs/reference/request.json` is a spec-spine 166 3.2 request:

- `schemaVersion` `1.0.0`, `outputDir` `docs/reference`;
- `specs` `{ "select": "all" }`, so a new spec gets a page with no edit here;
- `traceability` `false`: the corpus declares no spec-169 relations, and a
  supplied empty read would render `None declared.` on every page, which a
  reader could take for "untested". The page renders `Not supplied.`;
- `catalog` `null`: the corpus has no spec-162 operation catalog;
- no `limits` member: spec-spine's defaults (1024 pages, 512 KiB per page,
  256 signatures) hold. The largest page is about 40 KB.

### 3.2 Regeneration

`make refresh` runs, in order: `compile`, `index`, `reference generate
--request docs/reference/request.json`, `index`. Generation reads the fresh
registry and index; the pages are under `docs/`, a hashed input
(`spec-spine.toml` `extra_hashed_inputs`), so the second `index` records them.
The pages do not depend on the global inputs digest, only on each spec's
registry shard and its owned units' index shards, so a second `make refresh`
writes nothing (measured on 2026-11-10: 70 written, then 70 unchanged).

A change that edits a spec therefore commits the regenerated page with the
spec and its shards, exactly as it already commits the shards.

### 3.3 Generated, never edited

Every region but `notes` is rewritten from the model on each generation
(spec-spine 166 3.6), so a hand edit does not survive and the check refuses
it. When a page is wrong, the defect is in its source: the spec's frontmatter
or text, a claimed path, the index, or spec-spine itself. The fix goes there
and the page is regenerated. A spec-spine defect is reported upstream and
recorded in the implementation record; it is never patched in a page.

`notes` is the one authored region of each page, preserved across
generations. It is reviewed like any authored text (3.6).

### 3.4 Freshness

- `make gate` runs `spec-spine reference check --request
  docs/reference/request.json` after its existing steps. The check never
  writes.
- `make reference-check` runs the same check alone. This spec's
  Verification runs it, so the merge queue and `main` run it in the
  acceptance partition.
- Increment 2: the `boundaries` job (`.github/workflows/boundaries.yml`,
  owned by spec `001`) installs the pinned spec-spine and runs `make
  reference-check`, so a pull request learns of a stale page before it is
  queued. The managed governance job runs `spec-spine check`, which does not
  read reference pages; until spec-spine or the setup profile can declare
  the reference check (3.7), this step is how a pull request runs it.

### 3.5 The directory index

spec-spine 166 3.1 generates no index page. `docs/reference/README.md` is
authored and stable: what a page holds, that pages are generated, how to
regenerate and check them, that `notes` is the only authored region, and
that `spec-spine registry list` (or each page's Lifecycle table) gives the
current status. It names no spec by number or status. GitHub lists the
directory's pages above it. `README.md` at the root links it.

### 3.6 Review

The AI review leaves out `docs/reference` (#586, A-92), the whole
directory. Every source a page is generated from (the specs, the claimed
code, the index inputs, the `Makefile` targets) stays under review. Three
authored things sit inside the excluded directory: `request.json`,
`README.md`, and any non-empty `notes` region. They are small and change
rarely; a change to any of them says so in its pull request description, so
a human reviews it. This spec adds no `notes` text.

### 3.7 Recorded follow-ups

Recorded for the tools, not specified here:

- spec-spine: an index page for an export (a table of id, title, status and
  implementation), so the directory index need not be authored.
- spec-spine: a declared export in `spec-spine.toml` that `spec-spine check`
  includes, so the managed governance gate checks pages with no repository
  step.
- spec-spine: page links between related specs (amends, amended by,
  depends on) in the `changes` region.
- statecraft-cli: a setup parameter that adds declared read-only governance
  checks to the managed governance job, and the review exclusion derived
  from a declared export's `outputDir` rather than listed by hand.

## 4. Out of scope

- Rendering the pages to a website or `docs.rs`.
- Traceability relations (spec-spine spec 169) and an operation catalog
  (spec 162).
- Any change to a spec's text to improve its page; such changes are made
  under the owning spec as usual.

## 5. Observable negative cases

- A spec edit committed without `make refresh`: `make gate` fails with
  `page-changed` (and `ledger-stale` for the shards).
- A hand edit in a generated region: `reference check` reports
  `page-changed` naming the region.
- A spec directory removed while its page remains with empty `notes`:
  generation removes the page; with non-empty `notes`, generation refuses
  (`page-orphaned`) until a human moves the text.

## Acceptance

1. `docs/reference/` holds one page per registry spec and `README.md`, and
   `make reference-check` exits 0 on the committed tree.
2. `make refresh` on the committed tree changes no file.
3. `make gate` includes the reference check.

## Decisions at approval

Decided in this text, with the reason beside each: every spec is exported
(3.1), so no edit is needed as the corpus grows; traceability and the catalog
are off (3.1), because an empty supplied read would read as "untested"; the
directory index is authored and lists no spec (3.5), because a hand-kept list
is what drifted in the README; the pages are excluded from the AI review
(3.6), because they are generated and a discrepancy is fixed in its source
(owner, 2026-11-10).
